# `/discuss` Skill Specification

## 1. Purpose

`/discuss` 用于在设计和实现之前，与用户共同明确需求、范围、约束和高层实现方向。

它的核心目标不是尽可能多地提问，而是：

> 通过调查现有上下文和逐步解决关键决策，消除会影响后续设计与实现的重要不确定性，直到 Agent 与用户形成明确且经过确认的共同理解。

`/discuss` 只负责回答：

- 我们到底要做什么？
- 为什么要做？
- 期望行为是什么？
- 哪些内容属于范围内？
- 哪些内容不属于范围内？
- 有哪些重要约束？
- 哪些关键决策需要用户决定？
- 大的实现方向是什么？
- 是否仍然存在会影响后续工作的未决问题？

`/discuss` 不负责回答具体如何实现。

具体文件修改、函数设计、数据结构、实现步骤等内容属于 `/design`。

---

## 2. Core Principle

`/discuss` 必须采用动态决策树，而不是固定问卷。

基本流程：

```text
用户提出需求
↓
调查已有上下文
↓
识别事实、探索问题与决策
↓
自己解决可以调查得到的事实
↓
识别仍然存在的重要探索问题或决策
↓
找到最上游、最重要的未决问题
↓
一次询问一个问题
↓
探索问题保持开放、中立，不提供推荐
决策问题提供 Agent 的推荐答案或 best guess
↓
用户回答或做出决定
↓
更新当前理解和决策树
↓
检查新的依赖、冲突、假设和 trade-off
↓
继续下一项重要决策
↓
不存在重要未决问题
↓
总结共同理解
↓
请求用户最终确认
↓
用户确认
↓
结束 /discuss
```

---

## 3. Dynamic Decision Tree

### 3.1 不使用固定问题清单

Agent 不得机械地依次询问：

```text
目标是什么？
用户是谁？
成功标准是什么？
技术栈是什么？
是否需要移动端？
是否需要权限？
是否需要缓存？
……
```

不同任务需要解决的问题不同。

Agent 应根据：

- 用户当前需求
- 项目已有实现
- 用户之前的回答
- 已经确定的决策
- 决策之间的依赖关系

动态决定下一步应该询问什么。

---

### 3.2 优先解决上游决策

如果问题 B 的答案依赖问题 A，则必须先解决 A。

例如：

```text
是否需要实时更新？
├── 否
│   └── 不需要讨论实时通信方式
│
└── 是
    ↓
允许多少延迟？
    ├── 秒级
    │   └── 可以考虑 polling
    │
    └── 接近实时
        └── 后续才需要讨论 SSE / WebSocket 等方向
```

不得在上游决策尚未确定时过早询问下游实现问题。

---

### 3.3 根据回答剪掉无关分支

如果一个决策已经使某些问题失去意义，则这些问题不得继续询问。

例如：

```text
移动端只需要查看
```

则不应该继续讨论：

```text
移动端编辑器如何设计？
移动端拖拽操作如何实现？
移动端复杂表单如何布局？
```

除非新的需求重新使这些问题相关。

---

## 4. Fact, Discovery Question, and Decision

这是 `/discuss` 的核心判断规则之一。

### 4.1 Fact

Fact 是可以通过现有环境调查得到的信息。

例如：

```text
这个项目使用 React 还是 Vue？
使用 npm、pnpm 还是 yarn？
数据库是什么？
当前 API 如何实现？
是否已经存在权限系统？
某个组件在哪里定义？
现有页面是否支持移动端？
```

对于 Fact：

> Agent 必须自己调查，不得优先向用户提问。

可使用：

- 代码搜索
- 文件系统
- 项目文档
- Git history
- 配置文件
- package metadata
- 测试
- 项目提供的工具
- 必要时的外部官方文档

---

### 4.2 Discovery Question

Discovery Question 用于获取只能由用户提供的真实问题、经历或期望结果。

例如：

```text
最近一次遇到这个问题是什么情况？
你当时具体怎么完成这个任务？
现有流程中哪里最浪费时间？
```

对于 Discovery Question：

> Agent 必须开放、中立地提问，不得先给推荐答案，并应优先询问近期真实案例，而不是假设性偏好。

---

### 4.3 Decision

Decision 是无法仅通过调查项目得到，并且最终应该由用户决定的选择。

例如：

```text
这个功能是否应该支持未登录用户？
是否需要兼容旧 API？
移动端是否需要完整编辑能力？
删除操作是否允许恢复？
管理员是否可以查看所有用户内容？
```

对于 Decision：

> Agent 可以提供分析、推荐和 best guess，但最终决定必须交给用户。

---

### 4.4 不确定问题类型

优先尝试调查。

只有在调查后仍然无法确定，并且答案会影响需求或方案时，才询问用户。

---

## 5. Question Selection

每一轮只能选择一个问题。

选择下一问题时，应按以下优先级判断。

### 第一优先级：会改变需求本身的问题

例如：

```text
这个功能实际上需要解决什么问题？
```

---

### 第二优先级：会改变范围的问题

例如：

```text
是否需要同时支持管理员和普通用户？
```

---

### 第三优先级：会改变关键行为的问题

例如：

```text
删除是永久删除还是可恢复？
```

---

### 第四优先级：会改变高层方案的问题

例如：

```text
数据是否必须实时同步？
```

---

### 第五优先级：重要约束

例如：

```text
是否必须兼容现有 API？
```

---

### 第六优先级：重要 trade-off

例如：

```text
这里更优先保证简单性，还是允许增加复杂度来支持未来扩展？
```

---

## 6. Question Quality

一个问题只有在答案可能实质影响以下至少一项时才值得询问：

- Goal
- Scope
- Expected behavior
- Key requirement
- Constraint
- High-level approach
- Architecture direction
- Compatibility
- Important trade-off
- Success condition

如果答案不会明显影响后续 `/design` 或 `/implement`，通常不应该询问。

---

## 7. One Question at a Time

一次只允许提出一个主要问题。

不得：

```text
你希望支持移动端吗？
需要管理员权限吗？
图片保存在哪里？
最大上传大小是多少？
需要 CDN 吗？
```

应该：

```text
这个功能是否需要完整支持移动端？

我的推荐：需要支持查看，但第一版不需要完整编辑能力。
原因是当前需求的核心操作发生在桌面端，而完整移动端编辑会显著扩大范围。

你希望：
A. 不支持移动端
B. 移动端只支持查看
C. 移动端完整支持

我推荐 B。
```

等待用户回答后，再决定下一问题。

---

## 8. Recommendation / Best Guess

每个 Decision 问题都应该尽可能附带 Agent 当前的：

- 推荐答案
- best guess
- 简短理由

推荐答案必须基于：

- 已有项目上下文
- 当前需求
- 已确认决策
- 现有架构
- 明确的 trade-off

不得为了显得有判断力而随意推荐。

如果证据不足，可以明确说明：

```text
目前没有足够信息让我明显倾向某一个方案。

如果必须先选，我倾向 B，因为它对现有系统的影响更小。
```

---

## 9. Prefer Concrete Choices When Helpful

如果 Agent 已经可以识别少量合理方案，应优先把开放问题转化为清晰选项。

例如避免：

```text
你希望权限系统怎么设计？
```

优先：

```text
目前有三个合理方向：

A. 所有登录用户权限相同
B. Student / Teacher 两种固定角色
C. 通用 RBAC

我推荐 B。

当前需求只有两种明确用户类型，没有证据表明现在需要通用 RBAC。

你希望采用哪一种？
```

但不得为了制造选择而提供虚假的选项。

如果问题本身适合开放回答，就保持开放问题。

---

## 10. Investigate Before Asking

在询问用户之前，Agent 应先检查：

```text
这个问题能不能通过项目本身解决？
```

调查重点包括：

```text
项目结构
已有实现
相关组件
相关 API
配置
数据库 schema
类型定义
测试
文档
Git history
类似功能
已有设计模式
```

例如不得问：

```text
这个项目使用 pnpm 吗？
```

如果仓库已经存在：

```text
pnpm-lock.yaml
packageManager: pnpm@...
```

---

## 11. Do Not Over-Interview

`/discuss` 不是无限采访。

Agent 不得因为“还能继续想到问题”就继续询问。

不得：

```text
还有什么可能的问题？
↓
再问一个
↓
再问一个
↓
继续寻找所有可能 edge cases
```

应该判断：

> 这个问题的答案是否可能改变后续设计？

如果不会，则停止询问该方向。

原则：

```text
Do not ask a question merely because another question can be asked.
```

---

## 12. Scope Control

`/discuss` 必须主动识别需求是否过大。

如果用户提出的需求实际上包含多个独立功能，例如：

```text
用户系统
课程系统
聊天
通知
统计
权限
```

Agent 不应该立刻进入各子系统细节。

应该先确认：

```text
这些内容是否属于同一个当前任务？
是否应该拆成多个独立任务？
当前 /discuss 应该覆盖哪些部分？
```

先控制 scope，再继续细化。

---

## 13. Detect Ambiguous Language

Agent 应主动识别缺乏明确含义的词，例如：

```text
modern
scalable
robust
fast
simple
user-friendly
secure
flexible
clean
enterprise-ready
best practice
```

不得直接把这些词当作明确需求。

例如用户说：

```text
需要 scalable。
```

Agent 应判断它实际可能代表：

```text
预计用户量？
并发量？
数据规模？
部署规模？
未来扩展要求？
```

然后只询问真正影响设计的部分。

---

## 14. Detect Assumptions

Agent 必须区分：

```text
用户明确说过的
项目中能够验证的
Agent 根据上下文推断的
仍然未知的
```

推断不得悄悄变成已确认需求。

重要推断如果会影响后续设计，应转化为 Decision 让用户确认。

例如：

```text
我目前的理解是，这个功能只面向管理员。

这是根据现有页面结构推断的，但你还没有明确确认。

这个理解正确吗？
```

---

## 15. Detect Contradictions

每次获得新回答后，Agent 应检查它是否与之前的决定冲突。

例如：

```text
之前确认：
必须完全离线工作

后来确认：
依赖云端 API
```

Agent 不得同时接受两个冲突条件。

应该指出：

```text
这里和之前确认的“完全离线”存在冲突。

如果使用云端 API，就无法满足严格离线要求。

我们需要确定哪一个要求优先。
```

然后将其作为新的上游 Decision 解决。

---

## 16. Detect Dependencies

每个 Decision 都可能影响其他 Decision。

Agent 应维护内部的依赖关系，例如：

```text
需要多人协作
↓
需要身份识别
↓
可能需要权限系统
↓
权限系统影响 API 和数据模型
```

但是 `/discuss` 只讨论到高层需求和方向。

详细的数据模型和 API 结构仍然留给 `/design`。

---

## 17. Trade-offs

如果不存在明显唯一正确的方案，Agent 应明确指出 trade-off。

例如：

```text
方案 A：
实现简单，但以后扩展成本较高。

方案 B：
当前实现更复杂，但以后增加角色更容易。

根据目前只存在两种角色的需求，我推荐 A。
```

不得只列优缺点而拒绝提供判断。

也不得替用户做最终 Decision。

---

## 18. High-Level Technical Direction

`/discuss` 可以讨论高层技术方向。

例如：

```text
实时更新还是定时刷新
本地存储还是服务器存储
沿用现有系统还是引入新的 subsystem
同步处理还是异步任务
继续使用现有权限模型还是扩展权限模型
```

但不能进入详细 implementation design。

---

## 19. Boundary with `/design`

`/discuss` 回答：

```text
What are we building?
Why?
What behavior do we want?
What constraints matter?
What major decisions have been made?
What high-level direction should we follow?
```

`/design` 回答：

```text
How exactly will we implement it?
```

因此 `/discuss` 不应该详细决定：

```text
修改哪些具体文件
创建哪些具体文件
具体函数名称
具体 class 结构
具体 type 定义
数据库字段细节
API endpoint 完整定义
逐步 implementation plan
逐文件修改计划
具体测试代码
具体代码实现
```

如果讨论过程中出现这些内容，只在必要时用于理解问题，不应继续展开成正式设计。

---

## 20. Read-Only Rule

`/discuss` 是严格只读阶段。

允许：

```text
读取文件
搜索代码
查看 Git history
查看配置
查看测试
查看项目文档
运行不会修改项目状态的分析命令
查阅必要的外部资料
分析架构
分析现有行为
```

禁止：

```text
修改文件
创建实现文件
删除文件
重构代码
修复 Bug
实现功能
修改配置
修改数据库
执行 migration
自动 format 导致文件变化
commit
push
创建 PR
```

---

## 21. No Prototype Implementation

为了回答问题，Agent 不得擅自创建 prototype 或临时代码。

如果某项事实只能通过实验验证，并且实验会修改工作区，应说明：

```text
这个问题无法仅通过当前只读调查确认。

验证它需要修改或运行具有副作用的操作，因此不属于 /discuss 当前允许的操作范围。
```

然后根据重要性决定是否向用户确认下一步。

---

## 22. Discussion State

Agent 在讨论过程中应持续维护当前理解。

至少应内部跟踪：

```text
已确认的事实
已确认的决策
仍未确认的重要决策
约束
范围
高层方向
假设
冲突
依赖关系
```

不要求每一轮都把完整状态输出给用户。

只有在：

- 需要说明冲突
- 需要解释为什么提出某问题
- 用户要求查看当前状态
- 即将结束 `/discuss`

时再进行适当总结。

---

## 23. Completion Condition

不得使用以下条件判断 `/discuss` 完成：

```text
问完固定数量的问题
所有可能问题都讨论过
已经讨论了足够长时间
Agent 想不到任何新问题
```

正确结束条件是：

> 不再存在会明显影响后续设计的重要未决问题。

此时 Agent 应能够明确理解：

```text
目标是什么
范围是什么
主要期望行为是什么
关键约束是什么
重要决策是什么
高层实现方向是什么
是否仍存在需要明确记录的未知项
```

---

## 24. Final Confirmation

即使 Agent 判断已经达到 shared understanding，也不得直接结束。

必须先进行最终确认。

流程：

```text
Agent 判断：
没有重要未决问题
↓
总结当前理解
↓
说明关键需求和关键决策
↓
列出仍然存在但不会阻碍后续工作的未知项，如果有
↓
询问用户当前理解是否准确
↓
等待用户明确确认
```

用户可以：

```text
确认
修正
补充
否定某个决策
提出新的约束
```

如果用户进行修正：

```text
更新理解
↓
必要时重新进入决策树
↓
解决新的重要未决问题
↓
再次进行最终确认
```

只有用户确认以后 `/discuss` 才正式完成。

---

## 25. Final Output

最终输出不使用强制固定模板。

Agent 应根据任务复杂程度，自然总结已经确认的内容。

最终总结必须做到：

- 明确
- 简洁
- 不遗漏关键决策
- 不重复整个讨论过程
- 不输出无内容的固定章节
- 明确指出未解决的问题，如果仍然存在
- 足以让后续 `/design` 理解当前已经确认的需求

简单任务可能只需要：

```text
已确认：

- 新功能只面向登录用户。
- 移动端只需要查看，不支持编辑。
- 保持现有权限模型，不引入 RBAC。
- 数据不要求实时更新。
- 不改变现有 API 的兼容行为。

高层方向是继续扩展现有系统，而不是建立新的 subsystem。
```

复杂任务可以自然增加更多结构。

---

## 26. Prohibited Behaviors

### 禁止固定问卷

不得机械检查预先定义的所有问题。

---

### 禁止一次提出多个独立问题

除非这些内容实际上只是同一个 Decision 的选项或必要说明。

---

### 禁止询问可以自己调查的 Fact

优先使用项目和工具解决。

---

### 禁止未经确认做重要假设

推断必须保持为推断。

---

### 禁止替用户决定重要 Decision

Agent 可以推荐，但 Decision 属于用户。

---

### 禁止没有依据的推荐

推荐必须解释依据。

---

### 禁止过度采访

没有实质影响的问题不问。

---

### 禁止过早进入实现细节

详细实现属于 `/design`。

---

### 禁止修改工作区

整个 `/discuss` 严格只读。

---

### 禁止为了完整而扩大范围

只讨论当前任务真正需要解决的问题。

---

### 禁止忽略冲突

发现两个要求不兼容时必须明确指出并解决。

---

### 禁止把模糊词直接当成需求

必须确定这些词实际代表的行为或约束。

---

### 禁止在用户最终确认前结束

shared understanding 必须得到用户明确确认。

---

## 27. Recommended Interaction Pattern

推荐先判断问题类型，再按对应方式交互：

```text
必要的上下文说明

一个主要问题

如果是 Discovery Question：开放、中立，不提供推荐，并优先询问近期真实案例

如果是 Decision：Agent 的推荐答案 / best guess

简短说明为什么这个答案会影响后续工作

等待用户回答
```

Decision 例如：

```text
现有代码中，所有管理页面目前都要求登录，因此“是否登录”已经可以从项目中确认，不需要再问。

现在真正需要决定的是移动端的功能范围。

这个功能在移动端需要什么能力？

A. 不支持移动端
B. 只支持查看
C. 与桌面端一样支持完整编辑

我推荐 B。

原因是当前核心编辑流程明显针对桌面端设计，而支持查看可以满足移动访问需求，同时避免第一版扩大编辑器的实现范围。
```

然后停止，等待用户回答。

## 28. Mental Model

`/discuss` 不应该像：

```text
需求调查表
```

也不应该像：

```text
自由 brainstorming
```

更接近：

```text
Research
↓
Identify uncertainty
↓
Resolve the highest-impact decision
↓
Update understanding
↓
Repeat
↓
Confirm shared understanding
```

最终目标是：

> 用尽可能少但足够关键的问题，把一个模糊需求逐步收敛成可以进入 `/design` 的明确需求。
